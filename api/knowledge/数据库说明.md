# SO 数据分析系统 · 数据库说明

> 初版生成于 2026-05-30 · **更新于 2026-07-19** · 生产库当前 **80 张表 + 6 视图**,按 11 个业务域组织
> 用途:AI 下次会话快速 onboard / 人工查阅字段口径与表间关系
> 数据库:SQLite `db/product_flow.db`(生产 `/opt/so-data-analytics/db/`,约 2.5 GB)

## 这是什么系统

浙江省区**大华分销渠道 SO(销售出库)数据分析平台**(Streamlit + SQLite)。
管理三层渠道:**一级代理商(~49 家)→ 服务商(~9,339 家)→ 终端用户**。

## 核心数据流(进销存闭环)

```
进货              出货           铺货                上线激活           盘库
dealer_purchase → product_flow → distribution_info → install_redpack → inventory_snapshot
(代理商进货)      (出货流向)      (上级→下级分货)      (红包扫码激活)     (代理商库存快照)
```

## 双口径(贯穿全系统的核心概念)

| 口径 | 表 | 含义 |
|---|---|---|
| **全量感知** | `product_flow` | 出货流向(发到渠道的全部) |
| **红包扫码** | `install_redpack` | 上线激活(终端实际装机扫码) |

绑定率 = 上线 ÷ 出货,衡量出货后真实激活程度。

## 主键口径(互查需对齐)

- **客户编码**:服务商/客户账号,形如 `1@20836821747`(带 @)或 `1-145PBP`(短码 CRM 编码)
- **物料号 / 产品料号**:产品 SKU 唯一标识,JOIN product_focus 看专项
- **产品序列号**:单台设备唯一,贯穿出货/上线/盘库
- ⚠️ 同一实体可能有多个名字(如服务商改名、空格差异),按客户编码关联比按名字稳

### 市场推广专题批量导入（独立入口）

「📣 市场推广费用与 SO 效率」页面支持一次上传下面 6 类 Excel。该入口独立于通用 `_smart_import.py`，实现见 `src/_marketing_roi.py`，命令行入口为 `migrations/import_marketing_roi.py`。

| Excel 源表 | → 库表 | 粒度 | 更新规则 |
|---|---|---|---|
| 市场推广费用_城市维度分析 | `marketing_region_snapshot` (`source_type='city'`) | 快照日 × 城市 | 同快照日、同来源整体替换 |
| 市场推广费用_区县维度分析 | `marketing_region_snapshot` (`source_type='district'`) | 快照日 × 城市 × 区县 | 同快照日、同来源整体替换 |
| 市场推广费用_一级客户维度 | `marketing_dealer_snapshot` | 快照日 × 代理商业务/渠道拆分行 | 保留拆分明细，展示时按代理商汇总 |
| 市场推广费用_服务商维度 | `marketing_provider_snapshot` | 快照日 × 门头服务商 | 同快照日整体替换 |
| 会议分析 | `marketing_meeting_snapshot` | 快照日 × ADSPID（会议） | 同快照日整体替换 |
| 会议沙龙参会客户明细表 | `marketing_meeting_attendee` | 快照日 × 会议 × 客户 × 账号/参与人 | 保留同一会议同一公司的多人参会记录 |

- 快照日期从文件名最后一个 `YYYYMMDD` 解析；文件必须带日期。
- 6 个文件先解析、预览并做跨文件金额勾稽，再在**同一事务**内写库；任一文件失败则整体回滚。
- `marketing_import_batch.file_sha256` 保存文件指纹。完全相同的文件再次上传自动跳过；同一快照日、同一来源的新版本会替换旧快照并将旧批次标记为 `superseded`。
- 城市、区县、代理商、服务商是同一批费用的不同观察层级，**禁止跨层级相加**。全省/城市/区县总费用以 `marketing_region_snapshot` 为准，代理商与服务商表只用于分摊和下钻。

- **按整月更新**：探测本批数据出现的月份，`DELETE` 库里这些月 + **纯 `INSERT`**（先删整月保证幂等，绝不跨月误删）。visit_record 代理商/大华两侧按「打卡人所属公司」是否为空区分，互不影响。
- **全量替换**：`DELETE` 全表 + `INSERT`（distribution_info 另写入「数据时点=导出日期」列）。

## 域 1：基础数据（核心明细）

本域是整个 SO 数据分析平台的事实底座，存放序列号级别的最细粒度明细。其中 `product_flow` 与 `install_redpack` 构成平台的 **"双口径"核心**——同一台设备从"出货"到"上线"的两种感知方式：

- **出货流向（全量感知口径）**：`product_flow`，覆盖所有出库设备的上线感知，是设备流通的全量视角。
- **上线激活（红包扫码口径）**：`install_redpack`，仅覆盖通过安装红包扫码上线的设备，口径更窄但带激活/红包行为。

两表通过 `产品序列号` 关联，是"出货 vs 上线"对账、上线率、激活率分析的数据基础。所有上层页面**统一读 `_v` 视图**（而非原表），视图在 SQL 层补齐了上线年月、是否签约、签约状态、区县全名等派生字段，避免各页面重复实现口径逻辑。

### product_flow（859,895 行）

- **用途**：产品出货流向明细，序列号级。记录每一台出库设备的产品属性、出库客户、出库时间，以及该设备后续的上线省市区县、点亮/上线时间、是否异地上线等。是**全量感知口径**——只要设备出库即在表内，上线信息按系统感知能力回填。
- **数据来源**：360 报表（公司产品流向报表）导出的全量明细，序列号粒度。
- **更新方式**：全量替换（无 `数据时点` 字段，按整表刷新）。
- **关键字段**：

  | 字段 | 类型 | 含义（结合样本推断） |
  |------|------|------|
  | ID | TEXT | 记录唯一 ID（如 `b7007b53e37e46a380e631`） |

### visit_record（44,129 行）

- **用途**：业务员跑动打卡明细。记录每次拜访的客户、拜访时间、拜访目的与结果、打卡人、打卡地点及距离偏离等。日志型明细表。
- **两类业务员（按 `打卡人所属公司` 区分，数据源不同）**：
  - 🏪 **分销商业务员**（`打卡人所属公司` **非空** = 代理商业务员）：来自**拜访活动明细表**（360 报表导出），数据准确，继续使用。

### 视图：product_flow_v、install_redpack_v、visit_record_v

代码层统一读视图，原表只做存储。三个视图在原表基础上叠加 SQL 派生字段：

**product_flow_v**（基于 product_flow）

- 时间派生：`上线年月`（YYYY-MM）、`上线日期`、`上线年份`、`上线月份`
- `流通天数`：`上线时间 − 出库时间` 的天数，仅当结果在 0~730 天内才计，否则记 NULL（剔除异常）

- `KPI金额`：**公司口径金额**，优先取红包表（install_redpack 按序列号聚合的）`产品现有分销价`，缺失再 fallback 主表 `最新分销价`——这是 product_flow 与 install_redpack 在视图层的关键 join

**install_redpack_v**（基于 install_redpack）

- 时间派生：`上线年月`、`上线日期`、`上线年份`、`上线月份`
- `安装区县_全`：`安装城市 / 安装区县`（用安装侧地址，空值补"未知"）
- `是否签约`：1/0，当 `所属一级客户` 非空 **且**（去除空格/换行后）`出货客户名称` == `所属一级客户` 时为 1——即设备从其签约的一级代理商处采购
- `签约状态`：三分类——`无签约`（所属一级为空）/ `签约采购`（出货客户 == 所属一级）/ `跨渠道采购`（二者不等）

**visit_record_v**（基于 visit_record）

- `拜访时间_修正`：`COALESCE(活动创建时间, 拜访时间)`——因原 `拜访时间` 仅到日（08:00:00 占位），改用精确到分钟的 `活动创建时间`

- `_是否大华` / `_打卡方`：`打卡人所属公司` 为空 = 大华内部（🏢 大华），否则代理商（🏪 代理商）
- `_打卡异常无效`：1/0，异常类型属于"系统客户地址信息维护错误/客户多地址办公"等已知数据问题（非业务员造假）时为 1
- `_真异常打卡`：1/0，`距离偏离_米 > 1000` 且不属于上述已知数据问题时为 1

## 域 2：服务商

> **业务定义**：服务商 = 二级客户，即终端安装商 / 工程商 / 门店等真正面向终端用户、扫码上线设备的渠道末梢（全省约 9,339 家签约）。其上级是一级代理商（分销商）。本域围绕「签约 + 采购行为 + 健康度 + 等级 + 标签（马甲/伞形/流失/竞品）+ 门头投资」展开，是 SO（设备上线）分析与渠道下沉运营的最小颗粒。
>
> **核心主数据表**：`provider_contract`（签约 + 采购行为快照，源 360 健康度 P6）、`provider_profile`（服务商画像档案）。
> **核心视图**：`provider_contract_v`（加规范客户分类）、`provider_tier_v`（按累计货值算等级）、`provider_tags_v`（多源标签聚合）。

### provider_tags_v (视图)

- **派生自**：6 个数据源 `UNION ALL` 聚合成统一的「客户编码 + tag_key」长表，给每家服务商打上多源标签。
- **聚合的 6 类标签**：
  1. **`vest`（马甲）** — 取 `vest_account` 全表（origin=imported）。
  2. **`closed`（无采购意向/流失）** — 取 `closed_provider` 且 `撤销时间 IS NULL`（origin=hybrid）。
  3. **`competitor_top`（竞品TOP）** — 取 `competitor_top_provider` 全表（origin=imported）。
  4. **用户分配标签** — 取 `provider_tag_assignment` 任意 `tag_key` 且未撤销（origin=manual）。
  5. **`umbrella`（伞形）** — 两路并入：
     - **5a 明确建组**：`provider_umbrella_member` JOIN `provider_umbrella_group`（均未撤销/未解散），标记来源 `group:{id}`（origin=manual，最高优先）。
     - **5b 启发式**：`provider_profile` 中「同老板姓名 + 同老板电话 ≥ 2 家」的账号（origin=heuristic），并**排除已在 5a 明确组里的**，避免双计。
  6. **`low_eff`（低效签约）** — `provider_contract` 中「签约 ≥60 天 但红包扫码上线 ≤2 台」（LEFT JOIN `install_redpack` 按上线客户编码计数，origin=heuristic）。
- **统一输出列**：`客户编码`、`tag_key`、`标记来源`、`标记人`、`标记时间`、`备注`、`origin`（imported / hybrid / manual / heuristic，标识标签可信度来源）。
- **用途**：服务商画面/雷达上一次性展示某客户的全部标签（马甲、伞形、流失、竞品、低效），无需逐表查询。

### provider_tier_v (视图)

- **派生自**：`install_redpack`（安装红包/上线明细表），按 `上线客户编码` 分组聚合。
- **核心逻辑**：以**累计上线货值**（`SUM(产品现有分销价)`）划档服务商等级，与签约表 `provider_contract.服务商等级` 是**两套口径**（本视图是货值实测口径，签约表是签约固化口径）。
- **派生字段**：
  - `客户编码` = `上线客户编码`；`上线客户名称` = `MAX(上线客户名称)`。
  - `上线累计` = `SUM(产品现有分销价)`（累计上线货值，元）。
  - `红包累计` = 中奖金额>0 部分之和。
  - **`服务商等级`**（货值口径）：
    | 累计上线货值 | 等级 |
    |---|---|
    | ≥ 30,000 元 | v4服务商 |
    | ≥ 10,000 元 | v3服务商 |
    | ≥ 1,000 元 | v2服务商 |
    | > 0 元 | 已激活 |
    | = 0 / 无 | v0未激活 |
- **用途**：用真实上线货值反推服务商活跃等级，做激活/分级运营与「签约等级 vs 实际货值等级」差异校验。
- **关联关系**：`客户编码` → 服务商主键，可与 `provider_contract` 按客户编码 JOIN 做双口径对比。

## 域 5：三大专项攻坚（M13）

> **业务背景**：M13 是浙江省区围绕三大战略专项（夜视王 / 无线 / 场景化）的攻坚业务域。
> 它通过四张「目标/配置表」自上而下层层拆解年度上线台数目标（专项 → 地市 → 月度节奏 → 业务员），
> 再借助一张「产品映射表」把销售明细（如 `distribution_info` 的物料号）归类到三大专项，
> 最后通过一张「业务员归属表」把代理商口径的实绩折算到大华业务员维度，

> 数据链条概览：
> `product_focus`（物料号→专项）→ 给销售明细打专项标签
> `focus_target`（专项×地市年度目标）→ `focus_rhythm`（月度占比）→ `focus_target_salesperson`（业务员级目标）
> `dahua_dealer_owner`（业务员↔一级代理商）→ 把代理商实绩归到业务员

## 域 6:目标/KPI/区县基础

本域是整个 SO 数据分析平台的**考核基准层**:它定义了"应该做到多少"——区县 SO 目标、各指标的月度节奏曲线、地市 SI 签约/实销任务、服务商签约与分级激活目标、营销动作目标,以及作为分母口径的区县市场基础数据(GDP/人口/安防体量)。这些表本身不含实际业绩,实际业绩来自明细/快照域;本域提供的是被对比的"目标值"和"节奏占比",上层看板的各类**进度条 / 完成率 / 是否达标**都由这里的目标乘以节奏算出。

**进度条核心算法(贯穿本域):**
> 应达成 = 年度目标 × `kpi_rhythm` 中该指标截至当前月份的**节奏占比累计**
> 进度条完成率 = 累计实际达成 ÷ 应达成

所有"是否达标""进度低于 90%"判断都基于这条公式,`kpi_rhythm` 是节奏曲线的唯一来源。

### kpi_targets (97 行)

- **用途**:存放浙江省 **97 个区县**的年度 SO(上线销售)目标金额,是区县级 SO 完成率、SO 进度条的分母基准。一行 = 一个区县一个年度的 SO 目标。

|------|------|------|
| 城市 | TEXT | 地市名,如 杭州市 |
| 区县 | TEXT | 区县名,如 萧山区 / 拱墅区 |
| 年度 | INTEGER | 目标年度,如 2026 |
| SO目标_万 | REAL | 该区县全年 SO 上线金额目标(单位:万元),如 萧山区 580、拱墅区 310 |

### marketing_target (194 行)

- **用途**:存放**区县级营销动作目标与已投入**,即每个区县在各类营销活动上"年度要做多少、已经做了多少"。194 行 = 97 区县 × 2 类活动。
- **数据来源**:营销动作目标由人工下达(年度目标),"已投入"为截至数据截止日期的执行进度快照(来自系统/360 报表汇总)。
- **更新方式**:目标按年度设定;`已投入` 随快照刷新,样本统一截止 2026-04-30,属定期快照覆盖。
- **关键字段**:
  - `城市区县`——区县(外键 → `district_base.城市区县`);
  - `活动类型`——实测两类:**圈子会议**、**门头建设**;

- **主键**:(城市区县, 活动类型)。

**本域使用要点小结**

3. 服务商 V2/V3/V4 是按**安装红包成交额**(1000–1万 / 1万–3万 / 3万+)分级,三档之和小于签约总数属正常。
4. 本域全部为人工/Excel 导入的目标与基础数据,低频、按年度全量维护,与高频明细/快照域(实际业绩)分开,二者相除才得到完成率与达标判断。

## 域 7：战役管理 + Admin待办

本域包含两条业务线：一是「战役管理」（campaign / campaign_target），用于把全省阶段性攻坚目标（如批发类铺货、海康份额抢夺）拆解到具体客户、责任人和时间节点上跟踪执行；二是「Admin 待办工作流」（admin_issue / admin_issue_task / admin_issue_log），是一套问题驱动的内部工单系统，按「背景 → 调研 → 思路 → 任务 → 执行 → 关闭」六阶段推进数据口径修正、异常排查、新功能等内部事项。后三张表仅 admin 角色可见。

### campaign（行数 2）

## 🎁 转化红包（大华业务员转化激励，活动 2025-06 起）

**业务**：公司给大华业务员发**月度红包配额**，业务员对接服务商时发**抵用券**（如 50 元券＝服务商激活 5 台设备解锁），服务商激活够台数 → 券「已兑换」（领到红包）。

## 域 11：市场推广费用与 SO 效率（2026-07-19 新增）

本域是「📣 市场推广费用与 SO 效率」专题的数据底座，统一保存市场费用的区域汇总、代理商分摊、服务商门头、会议汇总和参会人明细。它解决了旧数据分散在 `marketing_target`、`provider_storefront_invest`、`promotion_meeting`、`promotion_meeting_summary` 中，无法统一对账和按同一快照下钻的问题。

### 新旧表关系与权威取数顺序

| 分析问题 | 权威表 | 说明 |
|---|---|---|
| 全省/城市总费用 | `marketing_region_snapshot`，`source_type='city'` | 11 个地市相加；不再叠加代理商或服务商表 |
| 区县总费用 | `marketing_region_snapshot`，`source_type='district'` | 97 个区县；可与城市合计勾稽 |
| 费用分摊到哪些代理商 | `marketing_dealer_snapshot` | 只代表已分摊到一级客户的部分，可能小于区域总费用 |
| 哪些服务商获得门头投入 | `marketing_provider_snapshot` | 服务商门头明细；源文件有地市、没有区县 |
| 每场会议投入与转化 | `marketing_meeting_snapshot` | 一行一场会议，含费用、签到、转化、会后关联 SO |
| 每个参会人的行为与券 | `marketing_meeting_attendee` | 一行一参会账号/参与人；同公司多人参会全部保留 |
| 旧页面/旧逻辑兼容 | `promotion_meeting` / `promotion_meeting_summary` / `provider_storefront_invest` | 旧表继续保留，新的市场推广专题不以其作为主数据 |
| 年度动作目标 | `marketing_target` | 仅存区县门头/圈子会议年度目标与已投入，不是完整费用事实表 |

> **禁止重复累计**：城市、区县、代理商、服务商是同一批费用的不同视角，不是四类独立费用。总盘只能选择一个区域层级汇总；代理商和服务商表用于解释费用去向。

### marketing_import_batch（当前 6 行）

- **用途**：市场推广文件导入批次审计表。记录每个来源文件的快照日期、文件指纹、导入时间、行数、状态和解析提醒。
- **更新方式**：每次导入写一条。相同 SHA-256 文件且状态为 `success` 时跳过；同快照同来源被修订文件替换后，旧批次状态改为 `superseded`。
- **关键字段**：

| 字段 | 类型 | 含义 |
|---|---|---|
| `batch_id` | TEXT PK | UUID 批次号 |
| `snapshot_date` | TEXT | 文件名解析出的快照日期，格式 YYYY-MM-DD |
| `source_type` | TEXT | `city` / `district` / `dealer` / `provider` / `meeting` / `attendee` |
| `source_file` | TEXT | 原始 Excel 文件名 |
| `file_sha256` | TEXT UNIQUE | 文件内容指纹，用于幂等判断 |
| `imported_at` / `row_count` | TEXT / INTEGER | 导入时间与有效数据行数 |
| `status` | TEXT | `success`（当前有效）或 `superseded`（已被同快照新版本替代） |
| `warnings_json` | TEXT | 解析提醒 JSON，如代理商拆分行、多人参会记录 |

### marketing_region_snapshot（当前 108 行）

- **用途**：城市和区县两种区域粒度的费用与营销动作汇总快照。当前 108 行 = 11 城市 + 97 区县。
- **主键**：`(snapshot_date, source_type, row_key)`；`row_key` 是城市或“城市+区县”业务键的 SHA-1。
- **区域字段**：`legion`、`province`、`city`、`district`；城市行 `district` 为空。
- **费用字段**：
  - `total_invest`：市场总费用；
  - `material_invest` / `gift_invest` / `terminal_invest`：领料、积分商城礼品、终端推广三类一级费用；
  - `storefront_invest`、`provider_storefront_invest`：全部门头费用、服务商门头费用；
  - `meeting_invest`：推广会申请费用；
  - `exclusive_store_invest` / `security_center_invest` / `vehicle_ad_invest` / `outdoor_ad_invest` / `other_ad_invest`：其他终端推广费用。
- **产出与转化字段**：`provider_storefront_output`（门头服务商当年安装红包关联 SO）、`meeting_output_30d`（会后 30 天签到公司关联 SO）、`attendee_count`、`attendee_company_count`、`signed_rate`、`activated_rate`、`new_signed_count`、`new_activated_count`、夜视王/场景化/无线会议与上线台数、三类券发放/兑换数量。
- **关联关系**：`city/district` → `district_base`、`product_flow_v.上线城市/上线区县_全`；会议金额可与 `marketing_meeting_snapshot` 勾稽；服务商门头金额可与 `marketing_provider_snapshot` 勾稽。

### marketing_dealer_snapshot（当前 65 行）

- **用途**：一级客户（代理商）维度的市场费用分摊快照。源文件会按业务类型、渠道客户类型拆行，同一代理商编码可以有多行；页面展示时按 `dealer_code + dealer_name` 汇总。
- **主键**：`(snapshot_date, row_key)`。`row_key` 包含代理商编码、业务类型、渠道类型和源行号，避免把合法拆分行当作重复数据删除。
- **基本字段**：`business_type`、`dealer_code`、`dealer_name`、`owner`、`channel_type`、`signed_target_wan`、`performance_ytd`、`orders_ytd`、`fee_rate`。
- **费用字段**：`total_invest`、领料/礼品/终端推广，以及门头、专卖店、安防服务中心、圈子会议、地市推广会、车体/户外/其他广告的数量和金额。
- **使用限制**：源文件没有地市字段。页面的地市筛选通过该地市门头服务商所属代理商和会议主办方识别；区县只能使用会议主办方识别。代理商明细合计小于区域总费用时，差额视为“尚未分摊到一级客户的费用”，不得强行分配。

### marketing_provider_snapshot（当前 49 行）

- **用途**：获得服务商门头投入的客户明细，用于判断激活和门头产出投入比。
- **主键**：`(snapshot_date, row_key)`；`row_key` 由 `provider_code` 生成。
- **关键字段**：`city`、`provider_code`、`provider_name`、`dealer_name`、`storefront_invest`、`active_flag`（Y/N）、`annual_redpack_output`（当年安装红包关联 SO）。
- **使用限制**：源文件只有地市，没有区县；区县总览应读取 `marketing_region_snapshot` 的区县汇总，不能把全市服务商明细误当成所选区县。
- **关联关系**：`provider_code` → `provider_contract.客户编码` / `install_redpack_v.上线客户编码`；`dealer_name` → 代理商名称。

### marketing_meeting_snapshot（当前 106 行）

- **用途**：会议级推广费用与转化快照，一行一场会议。
- **主键**：`(snapshot_date, row_key)`；`row_key` 由 `adsp_id` 生成。
- **会议属性**：`adsp_id`、`cloud_meeting_id`、`meeting_source`、`activity_name`、`business_type`、`meeting_category`、`expense_composition`、省/市/区县、开始时间、主办代理商。
- **规模与转化**：报名公司、签到账号/公司、无法转化公司、V5~V0/未签约分布、签约率、激活率、会后新签/新激活。
- **费用与关联产出**：`meeting_expense`、`post_redpack_output`、200 元/50或100元/无线5元券的发放/兑换数量与金额、夜视王/场景化/无线产品上线台数。
- **关联关系**：`adsp_id` → `marketing_meeting_attendee.adsp_id`；`city/district` → 区域表；`host_dealer` → 代理商名称。

### marketing_meeting_attendee（当前 1,997 行）

- **用途**：会议参会账号/参与人明细，记录参会客户、报名/签到/评价、实时星级和激活、会后关联 SO、券码和专项产品上线。
- **主键**：`(snapshot_date, row_key)`。业务键优先使用 `adsp_id + customer_code + account`，账号为空时回退参与人或源行号。
- **为什么不沿用旧主键**：旧 `promotion_meeting` 使用 `(ADSPID, 参会客户编码)`，会把同一场会议同一公司的多人参会合并。新表把账号/参与人纳入业务键，2026-07-19 文件中 46 条此类多人参会记录全部保留；无客户编码但有报名/签到信息的行也不丢失。
- **关键字段**：`customer_code/name`、`participant_name`、`account`、`signin_company`、`channel_type_fixed`、`star_realtime`、`active_realtime`、报名/签到/评价时间、`post_redpack_output`、三类券编码/面额/状态、三专项上线台数。

### ROI 与效率口径

| 页面指标 | 公式 | 数据源 | 解释 |
|---|---|---|---|
| 同期区域 SO | `SUM(product_flow_v.最新分销价)` | 当年 1 月 1 日至快照日，按上线城市/区县 | 全量感知 SO，不是安装红包口径 |
| 费用 / SO | 区域市场总费用 ÷ 同期区域 SO | `marketing_region_snapshot.total_invest` ÷ `product_flow_v` | 费用强度，越高表示单位 SO 使用的市场费用越多 |
| 推广会产出投入比 | 会后 30 天安装红包关联 SO ÷ 会议申请费用 | `post_redpack_output / meeting_expense` | 关联产出效率，不代表因果增量或利润 |
| 门头产出投入比 | 门头服务商当年安装红包关联 SO ÷ 服务商门头费用 | `annual_redpack_output / storefront_invest` | 门头服务商关联产出效率 |

> 当前没有毛利、费用后的净利润和可比基线，因此页面使用“产出投入比”，不把它表述为财务利润 ROI；会后关联 SO 也不能直接解释为全部由会议增量带来。
