## 架构分层

```
pages/(38 个)          UI 入口,薄封装:require_auth() + 调 render/gather 函数
   ↓
业务模块(_panorama/_focus/_weekly/_inventory/_campaign...)   汇总数据 + 渲染
   ↓
数据访问层(_loaders + 各 _*_loader)   读 SQLite → DataFrame,含 scope 权限过滤
   ↓
SQLite(db/product_flow.db)   54 表 + 6 视图(_v 视图在 SQL 层下沉派生口径)
```

## 关键机制

- **全局缓存**:`load_*_shared()` 系列 + `@st.cache_data`,跨 page 复用,首次进任意页加载一次
- **口径下沉**:派生字段(KPI金额/签约状态/服务商等级/打卡异常)在 SQL 视图(`_v`)算好,Python 兜底
- **权限隔离**:`_apply_scope_filter` 按登录用户 scope(城市/区县/业务员/代理商)行级过滤;admin/manager 跳过
- **路由**:`_page_registry.py` 注册所有 page(file/title/url/group/role/keywords),侧边栏分组+权限+搜索靠它
- **内存优化**:高重复字符串转 category,数值 downcast

## 代码组 1：数据访问层（loaders）

数据访问层负责从 SQLite（`db/product_flow.db`）读数据、做派生与内存优化、返回 DataFrame 给各 page 使用。核心是 `_loaders.py`（全局共享缓存 + scope 权限过滤），各业务专用 loader 各自对应一个业务模块/页面，`_views.py` 在 SQL 层维护各派生字段的单一真相源（V2/V3 共用口径）。

总体架构：
- **加载入口**：所有 page `import` 同一组 `load_*_shared()` 函数 → `@st.cache_data` 全局缓存命中，跨 page 复用，首次进入任意页加载一次。
- **口径下沉**：派生字段（KPI金额、签约状态、流通天数、服务商等级、打卡异常等）已在 SQL 视图（`_v` 后缀）算好，Python 端只做兜底（视图缺列时 fallback 重算），保证 V2 看板与 V3 沙箱 AI 看到同一套口径。
- **权限隔离**：`_apply_scope_filter` 在每个 `load_*_shared` 的包装层注入，按当前登录用户的 scope（城市/区县/业务员/代理商白名单）行级过滤；admin/manager 与未登录开发模式跳过。
- **内存优化**：高重复字符串列转 `category`、数值列 downcast（float32/Int16），并用 monkey-patch 兜住 category 列在 page 里的常见写法（fillna / 字符串拼接）。

### _loaders.py

- **职责**：数据访问层核心。提供 7 张主数据表的全局共享加载器（`load_*_shared`）、scope 权限过滤机制、服务商等级（KPI 口径）与 RFM 共享算法，并在模块导入时对 pandas 打多个 monkey-patch 兜住 category 列的内存优化副作用。33 个函数中绝大多数是各表的 raw loader + scope 包装 + 内部 helper。

- **主要函数**：

| 函数（主要参数）→ 返回 | 说明 |
|---|---|
| `load_main_shared()` → DataFrame | 主表（product_flow_v 视图）：出货/上线/产品/KPI金额等。各 page 最常用的事实表 |
| `load_redpack_shared()` → DataFrame | 安装红包表（install_redpack_v）：最大表（约 42 万行），含签约状态/安装地理/中奖金额，SO 与 RFM 的数据底座 |
| `load_profile_shared()` → DataFrame | 服务商管理沙盘（provider_profile）：静态画像，无时间维度 |
| `load_contract_shared()` → DataFrame | 服务商签约明细（provider_contract）：基础信息 + 签约状态，跑动/采购指标不在此读 |
| `load_provider_master_shared()` → DataFrame | 合并视图：沙盘 + 签约 outer join on 客户编码 → 一张主档（沙盘优先、签约 fallback、`_来源_*` 标记来源） |
| `load_visit_shared()` → DataFrame | 业务员跑动打卡（visit_record_v）：含拜访时间修正、打卡方（大华/代理商）、真异常打卡判定 |
| `load_vest_shared()` → DataFrame | 马甲账号名单（已确认的代理商自有服务商），用于团伙识别 |
| `load_provider_tier_shared()` → DataFrame | 每服务商一行：客户编码 / 上线累计 / 红包累计 / 服务商等级（KPI 口径），优先读 provider_tier_v 视图 |
| `compute_rfm_shared(window_months, r_days, f_count, m_value)` → DataFrame | 基于红包表的统一 RFM 计算 + scope 过滤；底层 `_compute_rfm_shared_raw` 缓存全量，本函数包一层 scope |
| `categorize_rfm(rfm_df, *, r_days, f_count, m_value)` → DataFrame | 给 RFM 表打「RFM类别」（5 类 MECE：核心活跃/流失风险/培育/已流失/未采购），含默认阈值 60天/6次/1万 |
| `_apply_scope_filter(df, *, city_col, district_col, salesperson_col, dealer_col)` → DataFrame | **统一 scope 过滤入口**。空 scope / admin / 未登录原样返回，否则按各列白名单 isin 过滤 |
| `scoped_cities(all_cities)` → list | 城市下拉框便捷过滤：把全城市列表收敛到用户可见范围 |
| `_apply_tier_to_df(df, code_col)` → DataFrame | 用统一等级覆盖 df 的「服务商等级」列，原值存为「服务商等级_原始」 |
| `_kpi_tier_from_so(so_amount)` → str | 按上线金额累计返回标准等级名（v0未激活/已激活/v2/v3/v4） |
| `_fast_connect(path)` → Connection | 带 PRAGMA 调优（200MB 页缓存 / 1GB mmap / 内存临时表）的 SQLite 连接，比默认快 2-3 倍 |
| `_optimize_dtypes(df, categorize, to_float32, to_int16)` → DataFrame | 统一 dtype 优化：高重复字符串转 category、数值列 downcast |

  内部细节（不展开）：`DB_PATH`（`db/product_flow.db` 路径常量）、各表列并集常量（`MAIN_COLS` / `REDPACK_COLS` / `PROFILE_COLS` / `CONTRACT_COLS` / `VISIT_COLS` / `VEST_COLS`）、`_safe_categorize` / `_select_clause` 等小 helper；模块顶部对 `pd.DataFrame/Series.groupby`（默认 `observed=True` 防 category 笛卡尔积 OOM）、`fillna`、`__add__/__radd__`（category + 字符串自动转 object）的 monkey-patch。

- **scope 权限过滤机制（重点）**：
  - 每个 `load_*_shared` 实际上是「raw 缓存函数 + scope 包装函数」两层：模块底部把原始函数保存为 `_raw_load_*_shared`，再用同名包装函数覆盖。raw 函数带 `@st.cache_data`（全局缓存、所有用户共享内存），**scope 过滤在缓存之后的包装层做**，避免 cache_data 命中导致跨用户数据泄露。
  - 各表传入 `_apply_scope_filter` 的列名不同（主表 `上线城市/上线区县`、红包 `上线客户地市/上线客户区县`、拜访额外带 `打卡人姓名` 业务员列等）。
  - scope 来源于 `_auth` 模块（`current_user` / `is_admin` / `get_current_scope`）；任何异常都 try/except 兜底为原样返回，不因鉴权问题打挂数据加载。

- **被谁调用/依赖**：
  - **被调用**：几乎所有 page 的数据入口（SO/产品流向/服务商画像/RFM/拜访跑动/阵地沙盘等）；专用 loader（如 `_focus_loader` 等）依赖本模块的 `DB_PATH`。
  - **依赖**：`_auth`（scope 与登录态，运行时 import）；`_views.py` 产出的 `_v` 视图（视图缺失时回退原表 + Python 派生）；`pandas` / `streamlit` / `sqlite3`。

- **职责**：DB 视图层 —— V2 看板与 V3 沙箱共享口径的单一真相源。把原本散在 `_loaders.py` 的 pandas 派生逻辑（KPI金额/签约状态/打卡异常/服务商等级等）提到 SQL 视图（`_v` 后缀），让 V3 沙箱直接读 SQLite 的 AI 也能看到同一套派生，口径不分叉。

- **主要函数 / 视图**：

| 名称（主要参数）→ 返回 | 说明 |
|---|---|
| `ensure_views(conn)` → dict | 幂等重建所有视图（DROP+CREATE）；依赖原表不存在则跳过。返回各视图状态 |
| `view_status(conn)` → dict | 查每个视图是否存在 + 行数（debug 用） |
| `__main__` CLI | `python _views.py [db_path]`：重建并打印视图状态 |

  视图清单（`VIEW_REGISTRY` 按依赖顺序）：
  - `product_flow_v` — 主表 + 派生（KPI金额/产品系列_有效三层 fallback/上线区县_全/流通天数 0-730/上线年月年份日期），KPI金额 LEFT JOIN install_redpack 取产品现有分销价
  - `install_redpack_v` — 红包表 + 派生（是否签约/签约状态三分类/安装区县_全/上线年月）
  - `visit_record_v` — 拜访表 + 派生（拜访时间_修正取活动创建时间/打卡方/打卡异常无效/真异常打卡>1000m）
  - `provider_tier_v` — 服务商等级聚合（客户编码 → 上线累计/红包累计/服务商等级 v0-v4）

- **被谁调用/依赖**：`app.py` 的 Excel 导入流程末尾调 `ensure_views(conn)` 重建视图；`_loaders.py` 的各 `load_*_shared` 优先从对应 `_v` 视图读（视图缺失才回退原表）。口径常量（打卡异常类型、等级阈值、名称归一 `_NORM`）必须与 `_loaders.py` 保持一致。仅依赖 `sqlite3`。

## 代码组 2:全景分析核心(panorama)

这组模块是「地市 / 区县 / 代理商」三级全景图的实现，分为三层：

- `_panorama.py` —— **纯数据层**，把一个实体（地市 / 区县 / 代理商）的多维度指标一次性查出来，返回一个嵌套 dict，不碰 UI。
- `_panorama_ui.py` —— **渲染层**，把上面的 dict 渲染成 Streamlit 的多个 tab。
- `_provider_quick_view.py` —— **服务商速览卡组件**，点击任意服务商行后弹出的统一详情卡，被多个 page 复用。

三者通过 page 18/19/20 串起来：page 调 `gather_panorama()` 拿数据 → 传给 `render_panorama()` 渲染 → tab 内的表格点击行时调起 `provider_picker_with_card()` 弹速览卡。

### _panorama.py

**职责**：全景图共用数据层。给定一个实体（city，可选叠加 district 或 dealer）和评估期 `period_start ~ period_end`，统一查出 SO 增长、渠道健康度、服务商质量、红包投放、销售跑动、竞品开拓六大维度；代理商级别额外查业务对标、推广会覆盖、阵地沙盘三块。底层数据源主要是 `install_redpack_v`（红包扫码上线，服务商唯一标识用「上线客户编码」）和 `product_flow_v`（全量产品流向）两个视图，配合 `kpi_targets`/`kpi_rhythm`（目标与节奏）、`provider_profile`/`provider_contract`/`vest_account`（服务商档案与异常）、`visit_record_v`（拜访打卡）、`competitor_top_provider`（竞品）、`dealer_sandbox`/`dealer_battlefield`/`promotion_meeting`（代理商沙盘 / 战略 / 推广会）等表。

**实体过滤抽象**：三个内部 helper 统一封装各表的 WHERE 子句——`_pf_filter`（product_flow，代理商口径用「出库客户名称」，因为「所属一级客户」填充率仅 1.4%）、`_redpack_filter`（install_redpack，代理商口径用「所属一级客户」）、`_visit_filter`（visit_record，无代理商维度，且固定排除异常打卡）。这是「双口径」设计的根：全量感知（product_flow）做 SO 主口径，红包扫码（install_redpack）做服务商颗粒度分析。

**主要函数**：

| 函数(主要参数) → 返回 | 说明 |
|---|---|
| `gather_panorama(conn, city, *, district, dealer, period_start, period_end)` → dict | **唯一对外入口**。按场景（city / 区县 / 代理商）调度下面各 `_section_*`，组装成 `{_meta, so_growth, channel_health, provider_quality, redpack, sales_visits, competitor_top, [dealer_benchmark, promotion_coverage, battlefield]}`。后三块仅 dealer 级别有。 |
| `_section_so_growth(...)` → dict | SO 增长：当期金额/台数、同比、环比、当期应达成与完成率，外加年度目标 / YTD 应达成 / YTD 累计 / 年完成率（仅 city / 区县有目标，代理商无），近 12 月趋势，城市级附区县分布。同时给出双口径（全量感知 vs 红包扫码）和绑定率。 |
| `_section_provider_quality(...)` → dict | 服务商质量：当期活跃服务商数、等级分布（V4/V3/V2/已激活，按累计货值分档）、RFM 9 宫格、新增/持续活跃/沉睡（对比环期）、异常服务商计数、服务商个体明细（带 RFM）和沉睡明细。等级与 RFM 统一调 `_metrics_rfm`。 |
| `_section_redpack(...)` → dict | 红包投放：本实体 ROI（中奖金额/上线货值）vs 全省基线及偏离度、正偏离 Top50（红包多）/负偏离 Top50（红包少但上线高），并内嵌 666 大额红包审核结果。 |
| `_section_sales_visits(...)` → dict | 销售跑动：区分大华业务员 / 代理商业务员的人数、拜访量、Top 清单；city 级复用 `_visit_rfm_eval.overview_all_salespeople` 出大华跑动评估 Top15；dealer 级额外算「代理商业务员综合」（拜访×上线贡献合并、带状态标签）和「服务商×业务员跑动覆盖矩阵」。 |
| `_section_competitor_top(conn, city, district, dealer)` → dict | 竞品开拓：查 `competitor_top_provider`，给总数、总竞品体量、已混卖大华/纯竞品数、Top10 名单、城市分布。代理商维度该表无对应字段，返回 `不适用=True`。 |
| `_section_channel_health(...)` → dict | 渠道健康度：以 `2025-01` 至评估期前一月为基线期，对比评估期，算新增（进水）/流失（出水）/净增/管道扩张率；流失再做归因（真停采 vs 转向其他地区/代理商）并给转走去向 Top30；外加大商动向 Top10（基线+评估合并货值，带新晋/上位/掉队/退场状态）。 |
| `_section_battlefield(conn, city, dealer, ...)`（仅 dealer） → dict | 阵地沙盘：代理商旗下所有服务商 LEFT JOIN `dealer_battlefield` 战略档案，输出供行内编辑的「编辑表」、已建档统计（归属/价值分布、9 宫格、攻坚优先级名单、流失风险名单、全档案明细）。表不存在返回 `_no_table`。 |
| `_section_promotion_coverage(conn, city, dealer, ...)`（仅 dealer） → dict | 推广会覆盖：旗下活跃/全历史服务商数、参会服务商数与覆盖率、场次列表、参会明细、未覆盖高价值服务商 Top20。 |
| `_section_dealer_benchmark(conn, city, dealer, period_end)`（仅 dealer） → dict | 业务对标：代理商画像（`dealer_sandbox`）、签约目标 vs SI 进度（暂用红包扫码近似 SI）、本月 MTD/环比/同比、历史标杆、同地市横向榜单与排名。不在沙盘表返回 `_no_sandbox`。 |
| `list_districts(conn, city)` / `list_dealers(conn, city)` → list[str] | 给 page 的下拉框提供可选区县 / 代理商清单（按出货量降序）。 |

> 内部小 helper（`_entity_label` 拼实体标签、`_query_abnormal` 异常服务商计数、`_audit_666_visits` 666 中奖后到访审核、`_list_provider_period`/`_big_mover_compare` 渠道健康度子查询、`_empty_quality` 空结构）不单独展开，逻辑已并入上表对应 section。

**被谁调用/依赖**：被 `pages/18·🌆 地市全景.py`（只传 city）、`pages/19·🏘 区县全景.py`（city+district）、`pages/20·🏢 代理商全景.py`（city+dealer）三个 page 调用 `gather_panorama`（19/20 还各用 `list_districts`/`list_dealers`）。内部依赖 `_metrics_rfm`（`tier_of` / `r_bucket` / `f_bucket` / `calc_rfm` 等级与 RFM 分档）和 `_visit_rfm_eval`（`overview_all_salespeople` 大华业务员跑动评估）。

## 代码组 3:周报/月报/RFM

这组模块负责把数据库里的原始流向/红包/拜访记录,汇总成两份对外报告(SMB 主管周报、月度地市经营报告),以及一个被多处复用的 RFM 算法内核。设计上「算数」与「渲染」分离:`*_report.py` 把数字算准并返回纯 dict,渲染层(docx / V3 沙箱 AI)只负责拼装文档,不写 SQL。

数据库统一为 `db/product_flow.db`(SQLite),核心事实表:`product_flow_v`(全量感知出货)、`install_redpack_v`(安装红包扫码上线)、`visit_record_v`(业务员拜访打卡)、`provider_contract`(服务商签约)、`kpi_targets`/`kpi_rhythm`(SO 目标+节奏)、各类月报快照表(`city_snapshot_p3`/`dealer_snapshot_p4`/`dealer_si_snapshot`)。

### _metrics_rfm.py

- **职责**: RFM 相关算法的「单一真相源」。集中定义所有阈值(R 阈值、等级金额线、效果窗口),并提供客户状态判定、等级判定、RFM 计算、拜访结果 7 分类、漏跑判定、9 宫格标签。改任何阈值只改这一处,全系统跟着变。

- **主要常量**:
  - `R_THRESHOLD=30`(活跃/流失 + 救援/维护意图的单一分界)、`EFFECT_WINDOW_DAYS=30`(拜访后效果窗口)、`F_RESCUE=3`
  - 等级金额线 `TIER_V4_FLOOR=30000` / `TIER_V3_FLOOR=10000` / `TIER_V2_FLOOR=1000`(单位:元,基于近 12 月累计货值)
  - 9 宫格可视化档位 `R_VISUAL_GREEN/YELLOW=30/90`、`F_VISUAL_HEALTHY/BAD=12/3`
  - 7 类拜访结果标签常量 `LABEL_RESCUE_SUCCESS/FAIL/NORMAL/LOST/NEW/OFFICE/PENDING`(供外部 equals/startswith 匹配)
  - 文件尾部保留旧名兼容别名:`_level=tier_of`、`R_HEALTHY/R_WARN=R_THRESHOLD` 等

- **主要函数**:

  | 函数(主要参数) → 返回 | 说明 |
  |---|---|
  | `customer_status(R, cum_val)` → str | 客户 3 档状态:💤未激活(累计货值≤0) / 🚨流失(R>30) / 🟢活跃 |
  | `is_lost(R, cum_val)` / `is_active(R, cum_val)` → bool | 流失 / 活跃布尔判定,二者互斥 |
  | `tier_of(cum_val)` → str | 累计货值 → 等级 V4/V3/V2/已激活/v0 |
  | `tier_case_sql(col)` → str | 生成与 `tier_of` 同阈值的 SQL CASE 表达式,供查询内直接套等级 |
  | `r_grade/f_grade/m_growth_grade(x)` → str | 单值 → 🟢🟡🔴 短标 |
  | `r_bucket/f_bucket(x, style)` → str | 单值 → 9 宫格分桶标签(`long` 带区间文字 / `short` 仅 emoji) |
  | `calc_rfm(activities, asof, window_days=365, with_growth)` → dict\|None | 给定某客户上线明细 DataFrame,算 asof 时点的 {R, F, M_cur, M_万, M_prev, M_growth, _last_active} |
  | `is_rescue_intent(R, F)` → bool | 拜访那一刻是否属救援意图(R>30 或 F<3) |
  | `classify_visit(visit_row, activities_by_code, db_max_dt, period_end_dt, sp_dealers, vest_codes, ...)` → dict | 单次拜访的 7 分类核心算法,返回 {分类, 拜访意图, 结果, 依据, 马甲标识} |
  | `is_missed(rfm_start, rfm_end)` / `missed_severity(rfm_end)` → bool/str | 漏跑判定(期初活跃→期末流失+有货)及严重度(V4/V3=🚨严重) |
  | `nine_cell_label(r_b, f_b)` → str | (R 桶, F 桶) → 业务标签(如「核心客户」「沉睡待救援」),映射表 `NINE_CELL_LABEL` |

- **被谁调用/依赖**: 纯算法模块,仅依赖 pandas。是本组乃至跑动相关功能的公共内核,被 `_visit_rfm_eval`、`_monthly_city_report`、`_panorama`、`_task_manager`、`_provider_quick_view`、`_focus_section` 直接 import。其中 `classify_visit`/`calc_rfm` 是拜访评估主路径,`tier_of`/`tier_case_sql`/`NINE_CELL_LABEL` 被各全景/月报页用于等级与 9 宫格。

### _visit_rfm_eval.py

- **职责**: 业务员「跑动 RFM-Impact 评估」的数据查询 + 适配层。本身不含算法(全部委托给 `_metrics_rfm`),负责从 DB 取某业务员的责任范围(scope)、当期拜访、历史拜访、相关客户上线明细,逐次调用 `classify_visit` 完成两步评估(拜访分类 + 漏跑识别),并产出排行榜。page 06 与月报 2.2 共用。

## 代码组 4:专项攻坚(focus)

「专项攻坚」是把出货、上线、跑动、推广会、目标这几条数据线，围绕一个**产品专项**（夜视王 / 无线 / 场景化）穿透汇总的一组模块。三个专项各有一个 page，但共用同一套数据层（`_focus_section`）和 UI 层（`_focus_ui`），服务商打标功能由独立的 `_tag_widget` 提供。专项的口径是「物料号」——`product_focus` 表把物料号映射到专项，再用物料号 JOIN 回各业务数据源。

### _focus_section.py

**职责**:专项数据穿透的纯数据层。给定一个专项 + 评估期 + 可选地市/代理商，跨 5 个数据源（产品流向 / 红包上线 / 跑动 / 推广会 / 专项映射）+ 目标系列表，一次性算出该专项的全部分析维度，返回一个嵌套 dict（无任何 UI）。

**主要函数**:

| 函数(主要参数) → 返回 | 说明 |
|---|---|
| `gather_focus_data(conn, focus, period_start, period_end, city=None, dealer=None)` → `dict` | 唯一对外入口。一次查询拼出 10+ 个分析块，详见下表。`city`/`dealer` 作为实体过滤层层下推到每条 SQL。 |
| `shift_period(start, end, months)` → `(str, str)` | 把起止年月整体平移 N 个月，用于算同比(-12)、环比(-n)区间。内部 helper。 |
| `n_months(start, end)` → `int` | 评估期跨几个月（含头含尾）。内部 helper。 |
| `calc_yoy(cur, base)` → `float \| None` | 通用增长率 `(cur-base)/base`，base 为 0/空时返回 None。内部 helper。 |

`gather_focus_data` 返回 dict 的主要键（块）：

| 键 | 内容 |
|---|---|
| `_meta` | 专项名、评估期、同比/环比区间、SKU 总数/在售数、地域口径、生成时间 |
| `kpi_overview` | 出货货值(product_flow)+同比/环比、上线货值(install_redpack)+同比、绑定率、红包额/ROI、活跃服务商数；并接 `focus_target` 年度目标 + YTD 实绩 + 完成率 |
| `monthly_trend` | 近 12 月出货 vs 上线货值走势（两源 outer merge） |
| `city_breakdown` | **仅全省视图**输出 11 地市分布：评估期出货/上线/绑定率 + YTD vs 地市目标 + 完成率 |
| `dealer_top` | Top 20 代理商（按出货货值，product_flow 出库客户口径） |
| `provider_top100` | Top 100 服务商（按上线货值，install_redpack 上线客户口径） |
| `sku_top50` / `sku_status` | Top 50 型号销售排行 + 全部 SKU 的产品状态分布 |
| `visit_coverage` | 卖该专项的服务商中，被大华业务员 / 代理商业务员 / 任一到访的覆盖率（按 `_打卡方` 区分口径） |
| `promotion_coverage` | 这批服务商历史参加过推广会的覆盖率（JOIN promotion_meeting） |
| `provider_tier` | 这批服务商按累计货值的 RFM 等级分布（调 `_metrics_rfm.tier_of`） |
| `monthly_rhythm` | **月度节奏 vs 实绩**：`focus_rhythm` 节奏% × 地市年度目标 = 月度目标，对比 product_flow 月度实绩，含累计完成率 |
| `salesperson_breakdown` | **业务员维度**：基于 `focus_target_salesperson` 做地市级目标分解，实绩为估算口径（总负责=地市 YTD 全量；分担=地市 YTD×占比%） |

实现要点：实体过滤(city/dealer)为各源拼出不同的 where 片段（product_flow 用「上线城市/出库客户名称」、install_redpack 用「上线客户地市/所属一级客户」、visit 用「拜访客户城市」），无过滤时退化为 `1=1`；`monthly_rhythm` 和 `salesperson_breakdown` 用 try/except 包裹，对应的 `focus_rhythm` / `focus_target_salesperson` 表未建时静默返回 `[]`，不影响其余块。

**被谁调用/依赖**:被 `_focus_ui._cached_focus_data` 调用（即三个专项 page 的唯一数据来源）。依赖 `_metrics_rfm.tier_of` 做服务商等级划分；依赖库内表/视图 `product_flow_v`、`install_redpack_v`、`visit_record_v`、`promotion_meeting`、`product_focus`、`focus_target`、`focus_rhythm`、`focus_target_salesperson`。

## 代码组 5：AI/LLM/Agent

这组模块构成 SO 数据分析平台的全部 AI 能力，覆盖三条互相独立的技术路线：

- **OpenAI 协议路线**（`_llm.py` + `_llm_tools.py`）：兼容 Kimi/通义/豆包，做 Function-Calling Agent 和单轮调用，给「智能搜索」做语义重排。
- **Anthropic 协议路线**（`_anthropic_client.py`）：requests 直连 Claude-compat 端点，复用 AI 代码助手的 `anthropic_config.json`，供「会议纪要校验」做多轮 tool-use 审计。
- **Docker 沙箱 Code Agent 路线**（`_code_agent.py`）：在容器里跑 Claude Code CLI，是 page 09「AI 代码助手」和 page 10「月度报告」的真正执行引擎。

`_ai_log.py` 是这组里最大的文件（2816 行），但它远不止「AI 日志」——它实质上是整个平台的 **SQLite 建表 + 迁移 + 业务侧写库总线**：所有 AI 日志、Code Agent 日志、月报归档、用户/权限、跑动任务、服务商标签体系（含伞形组）都在这里建表和 CRUD。`_ai_search.py`（智能搜索）、`_ai_handoff.py`（V2→V3 上下文交接）、`_task_manager.py`（跑动任务生成/核验）是围绕这条线的应用层。

### _anthropic_client.py

- **职责**：不引入 anthropic SDK，用 `requests` 直连 Anthropic Messages API（或兼容端点），复用 AI 代码助手的 `anthropic_config.json` 配置。支持单轮调用和多轮 tool-use 循环，主要给会议纪要校验用。
- **主要函数**：

| 函数(主要参数) → 返回 | 说明 |
|---|---|
| `is_configured()` → bool / `get_config()` → dict | 检查并读取 `anthropic_config.json`（base_url/auth_token/model），复用 `_code_agent.load_config` |

| `extract_text(response)` → str / `extract_tool_uses(response)` → list | 从 response.content 抽 text block 拼接 / 抽 tool_use blocks |

### _llm.py

- **职责**：OpenAI 兼容协议的统一 LLM 调用层。内置三家提供商定义（Kimi/通义千问/豆包），配置持久化到 `~/.so_data_analytics/llm_config.json`（chmod 600）。提供单轮 `call_llm` 和 Function-Calling Agent 循环 `call_agent`（含 SO 业务专用 system prompt）。
- **主要函数**：

| 函数(主要参数) → 返回 | 说明 |
|---|---|
| `load_config()` / `save_config(config)` / `get_active_config()` → dict\|None | 读写配置；返回当前激活提供商的 base_url/api_key/model（缺 key 返回 None） |

### _llm_tools.py

- **职责**：给 LLM Agent 调用的「工具集」。每个工具 = OpenAI Function-Calling schema（给模型看的说明书）+ Python handler（查 SQLite，返回 JSON 友好结果）。复用 `_loaders` 的缓存加载器，统一截断返回行数、错误返回 `{error}` 不抛异常。
- **主要函数**：模块核心是 13 个工具（每个含 `xxx`/`XXX_SCHEMA`），分四类——

| 类别 | 工具 → 返回 | 说明 |
|---|---|---|
| 实体查询 | `lookup_provider` / `get_provider_profile` / `lookup_dealer` / `lookup_visitor` | 模糊搜服务商（红包+沙盘+签约多源合并）、拉完整画像（含等级/RFM/马甲）、搜代理商、搜业务员 |
| 业务数据 | `query_online_records` / `query_visit_records` / `query_redpack_records` / `query_provider_kpi` | 按客户编码查上线/拜访/红包记录（可时间过滤、分组），查 KPI 等级/RFM |
| 排行聚合 | `top_n` / `compare_periods` | 通用 Top N（服务商/代理商/区县/产品/型号/业务员 × 台数/金额/红包）、两时段同环比对比 |
| 关系挖掘+兜底 | `is_fake_provider` / `describe_schema` / `generic_sql` | 假商判定（马甲/假签约）、返回库表结构说明、兜底执行只读 SQL |

| 注册/分发函数 | 说明 |
|---|---|
| `get_tool_schemas()` → list | 返回全部工具的 OpenAI schema 列表，喂给 LLM |
| `execute_tool(name, args)` → Any | 按名分发到对应 handler，异常包成 `{error}` |

- 安全要点：`generic_sql` 只允许 `SELECT`/`WITH`，用 `SQL_BLACKLIST` 正则拦 DROP/DELETE/UPDATE/INSERT/ALTER 等，只读模式连库（`file:...?mode=ro`），无 LIMIT 自动补 200；常量 `MAX_RESULT_ROWS=100` 限制返回体量。`DB_SCHEMA_DESC` 内嵌 6 张表的字段口径文档供模型参考。
- **被谁调用/依赖**：被 `_llm.call_agent`（OpenAI 路线）和 `_meeting_audit.py` / page 08（经 `_anthropic_client` 转协议后）调用。依赖 `_loaders` 的全部 `load_*_shared` / `compute_rfm_shared` 缓存加载器和 `DB_PATH`。

### _ai_search.py

- **职责**：把用户自然语言的模糊需求映射到具体功能 page。两段式策略：关键词初筛（永远跑，零延迟兜底）+ LLM 语义重排（已配置 LLM 时对前 N 条做精排），输出 top-3 推荐 page（带推荐理由）。

## 代码组 7:认证+首页+路由

这三个模块构成系统的「进门 + 落地 + 走向」：`_auth.py` 管谁能进、能看哪些数据；`_home.py` 是进门后的默认落脚页（数据导入 + 库表概览）；`_page_registry.py` 是全站页面的单一事实来源，侧边栏分组、权限过滤、智能搜索全靠它。三者都围绕 `app.py` 的 `st.navigation` 启动流程协作。

---

### _auth.py

- **职责**：登录鉴权 + 数据权限（scope）。负责门禁拦截、持久化登录（服务端 token 文件 + 浏览器 cookie）、当前用户/角色查询，以及按角色对 DataFrame 做行级数据过滤。三层认证回退：DB 用户优先 → `auth.json` 兜底 → 都没有则开发模式直接放行。

- **认证模型**：用户身份存于 `_ai_log` 的 DB（推荐，可在「用户管理」页维护），密码校验用 `hmac.compare_digest` 防时序攻击；角色与 scope 每次实时查 DB（管理员改权限后无需用户重登）。角色分 `admin` / `manager` / `salesperson` / `guest`，其中 `admin` 自动绕过所有 scope 过滤，其余角色按 `app_user_scope` 表的白名单（城市/区县/业务员/代理商）受限。

- **持久化登录**：登录成功生成 32 字节随机 token，写服务端 `~/.so_data_analytics/sessions.json`（chmod 600），同时用 `components.html` 注入 JS 在浏览器主文档写 cookie（`_so_da_token`，90 天）。后续访问从 `st.context.cookies` 读 token → 比对服务端文件 → 还原 `session_state`。服务端 token 永不过期，除非显式撤销或文件被删；校验 token 时顺带确认用户未被禁用。

- **主要函数**：

| 函数(主要参数) → 返回 | 说明 |
|---|---|
| `require_auth()` → None | **核心门禁**。各页面在 `set_page_config` 后立即调；未登录则渲染登录表单并 `st.stop()`，已登录或开发模式则放行 |
| `is_logged_in()` → bool | 是否已登录；无 session_state 时会尝试从 cookie 还原 |
| `current_user()` → str | 当前登录用户名（未登录返回空串） |
| `get_current_role()` → str | 当前用户角色（实时查 DB） |
| `is_admin()` → bool | 是否 admin（仅 admin 绕过 scope） |
| `is_privileged()` → bool | 是否 admin 或 manager（可分配任务、访问用户管理等） |
| `get_current_scope()` → dict[str, list[str]] | 当前用户数据权限白名单 `{scope_type: [values]}`；admin 返回空 dict 表示全放行 |
| `filter_by_scope(df, *, city_col, district_col, salesperson_col, dealer_col)` → DataFrame | **便捷过滤工具**。按当前用户 scope 过滤 df；admin/manager 直接返回原 df，其余按传入列名逐维过滤 |
| `logout()` → None | 撤销服务端 token + 清浏览器 cookie + 清 session_state |
| `render_user_badge()` → None | 侧栏底部展示用户名 + 登出按钮（可选调用） |
| `revoke_all_sessions_for_user(username)` → int | 强制某用户全设备下线（改密码时用），返回撤销数 |
| `list_active_sessions(*, username=None)` → list[dict] | 列出活跃 session（admin 用） |

- **职责**：系统主页 / 默认落地页。两大块——① 数据导入（多数据源 Excel 上传入库，支持 merge/append/replace 及多种专用导入流）；② 当前数据库概览（各表行数、时间覆盖、月度分布、服务商主档合并视图）。被 `app.py` 的 `st.navigation` 作为页面调用（import 时即执行顶层 Streamlit UI 代码）。

---

### 总体架构:page 是「薄壳」,逻辑在业务模块里

整个平台是一个 **Streamlit multipage app**。每个 `pages/*.py` 文件就是侧边栏里的一个菜单项,但它们**几乎不写业务逻辑**,典型结构只有三步:

1. `sys.path.insert(0, …/src)` —— 把 `src/` 加进 import 路径(因为 page 在子目录 `pages/`,要 import 平级的 `_xxx.py` 模块)
2. `require_auth()`(部分页再加 `is_admin()` 闸门)—— 登录鉴权
3. 选参 → 调一个或几个业务模块的 `render_*` / `get_*` / `gather_*` 函数 → 把结果交给对应的 UI 渲染函数

按「壳有多薄」可把 38 个 page 分成 4 档:

| 档位 | 代表 | 壳内代码量 | 模式 |
|------|------|-----------|------|
| **极薄壳** | 29/30/31 专项 | ~10 行 | `set_page_config` + 一行 `render_focus_page('主题')`,鉴权都在被调模块里 |
| **薄壳(选参型)** | 18/19/20 全景 | ~90 行 | `require_auth` → 选 地市/区县/代理商 + 月窗 → `@st.cache_data` 包 `gather_panorama` → `render_panorama` |
| **中壳(自渲染型)** | 库存/战役/搜索 | 数百行 | `require_auth`(+admin 闸)→ 调 loader 取数 → page 内直接用 `st.tabs/metric/dataframe` 排版 |
| **厚壳** | 02 智能分类(52KB)、03 假商治理(102KB)、12 产品流向(77KB)、13 评分、15 机会、🧪 实验室 | 数百~上千行 | 页内承载大量 RFM/团伙挖掘/透视/评分逻辑,与对应业务模块强耦合 |

**共性依赖**(几乎每个 page 都 import):
- `_auth` —— `require_auth / current_user / get_current_role / is_admin`(组:认证)
- `_loaders` —— `DB_PATH / scoped_cities`(组:数据加载,`scoped_cities` 按登录用户 data scope 过滤可见地市)
- 各自的业务模块 `_xxx.py`(组:业务逻辑)+ 对应的 `_xxx_ui.py` 渲染模块

**注册表 `_page_registry.py` 是单一数据源**:`app.py`、智能搜索、侧边栏导航都从它读 page 清单(file/title/url/group/role/keywords)。它本身不渲染任何 page,只是元数据 + 3 个工具函数。

### page 的典型函数面貌(模块级,不逐个写)

各 page 文件本身**对外不暴露函数**(Streamlit 是「从上到下执行脚本」模型,没有可被 import 的接口)。page 内出现的函数基本是两类内部 helper:

| 函数(主要参数) → 返回 | 出现位置 | 说明 |
|---|---|---|
| `month_range(start, end) → list[str]` | 18/19/20 等选月页 | 把起止月份展开成 `['2026-01','2026-02',…]` 填月份下拉 |
| `cached_panorama(…) / _overview(q) / _dazhi(q,th) …` | 全景页 / 库存页 | `@st.cache_data(ttl=600)` 包一层,缓存对 loader/`gather_*` 的调用,避免重复查 DB |

真正的取数与计算函数都在被调的业务模块里(`_panorama.gather_panorama`、`_inventory_loader.get_overview`、`_campaign_loader.get_kpi`、`_focus_ui.render_focus_page`、`_ai_search.search` 等),page 只负责「选参 + 调用 + 摆版」。

### 依赖关系小结

```
app.py / 侧边栏 / 智能搜索
        │ 读
        ▼
_page_registry.PAGES ──(file 路径)──► pages/*.py
                                          │ 每个 page:
                                          │  ① require_auth()        ← _auth
                                          │  ② scoped_cities/DB_PATH  ← _loaders
                                          │  ③ 调业务模块取数+渲染
                                          ▼
   _panorama(+_ui) / _focus_ui / _campaign_loader / _inventory_loader
   / _ai_search / _ai_log / _monthly_city_report / …(各业务模块)
```

- **被谁调用**:所有 page 由 `app.py` 经 `_page_registry` 路由后由 Streamlit 执行;`05/22` 之间存在页面跳转(全名册点客户名 → 画像页);`02/05` 与标签字典 `tag-dict`、伞形组 `umbrella-groups` 在「打标/伞形」数据上联动。
- **依赖什么**:统一依赖 `_auth`(鉴权)+ `_loaders`(DB 路径 / scope 过滤)+ 各自业务模块。极薄壳页(29/30/31)只依赖 `_focus_ui`;全景页(18/19/20)依赖 `_panorama` + `_panorama_ui` + `_monthly_city_report`(取地市/月份列表);战役页依赖 `_campaign_loader`。
