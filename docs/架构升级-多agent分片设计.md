# 架构升级思路:多 Agent 分片自治 + 能力调度

> 提出:金先生 2026-05-30 · 状态:🟡 待评估/设计(未实施)
> 背景:系统已 54 表 + 78 文件,继续增长会遇到 context 爆炸 + 需求路由不清

---

## 1. 要解决的真问题

1. **Context 爆炸**:数据库/表越来越多,不可能每次把全部 schema + 说明塞进单个 LLM session
2. **需求路由不清**:用户提需求时,不清楚该从哪个数据源、用什么口径取数最优

---

## 2. 金先生的原始构想(4 点)

1. 不能每次全塞 —— 按需加载
2. **分片自治 agent**:每个 agent 只管一个数据域(如"安装红包明细"专属 agent);该 agent 有大量固化的 CLI 命令应付 90% 固定需求;且能**自行新增 CLI 命令**
3. **调度层**(agent 或 skill):用户改需求时,它知道"哪个数据从哪个 agent 取更好"
4. 用这套思路重构开发框架,根治 context 爆炸 + 需求理不清

---

## 3. 我的评估

### ✅ 方向正确
这个构想跟业界正在收敛的 3 个方向高度一致(见 §4),解决的是真问题。核心洞察——**"分片自治 + 按需调度" 替代 "全量上下文"**——是对的。

### ⚠️ 要权衡的 5 个点

| # | 风险/权衡 | 建议 |
|---|---|---|
| 1 | **"agent 自行增加 CLI 命令"有失控风险** | 自主写代码=质量/安全隐患。改为「agent 生成 + 人审 + 固化」,不要全自主。固化的命令进版本库 |
| 2 | **调度准确性是最大难点** | "哪个需求找哪个 agent"本质是 routing/retrieval 问题,会路由错。需要每个 agent 有高质量「能力描述卡」(metadata),调度层基于语义匹配 |
| 3 | **跨域查询怎么办** | 大量真实需求要跨域 JOIN(如"业务员维度专项实绩"= install_redpack + product_focus + dahua_dealer_owner)。纯分片各管一摊会卡。调度层必须能**编排多 agent + 合并结果**,不只是单选一个 |
| 4 | **CLI 固化 vs 灵活查询要共存** | "90% 固定需求做成 CLI"对(沉淀高频);但剩 10% 长尾还要保留灵活 SQL/函数能力,否则遇到没固化的需求就卡死 |
| 5 | **过度工程风险** | 54 表是否已到必须重架构的规模?也许可先用轻量方案(分域文档 + 按需检索)过渡,验证后再上重型自治 agent |

### 我的核心建议:**渐进式,不要一次大重构**

分 3 步走,每步都能独立产生价值、可回退:

```
阶段 1(轻,1-2 周可做):分域文档 + 按需加载
  把已有的「数据库说明.md / 代码说明.md」拆成分域小文件
  + 一个「域索引」(每个域:管什么表/能回答什么问题/关键口径)
  LLM 先读索引 → 判断需求属哪个域 → 只加载该域文档
  → 立刻缓解 context 爆炸,零风险

阶段 2(中):每个域做成 MCP server / skill
  每个域(如安装红包)封装成一个 MCP server,暴露固化工具(=CLI命令)
  LLM client 按需连接,工具按需加载(deferred tools)
  → 这就是金先生说的"分片自治 agent + CLI 命令"的标准实现

阶段 3(重):调度层 + 跨域编排
  一个 router(skill 或 lead agent),读各域能力卡 → 路由/编排
  支持跨域:拆解需求 → 派给多个域 agent → 合并
  → 这就是"调度 agent"
```

---

## 4. 业界最佳实践对照(都是真实存在的)

金先生的构想几乎逐条对应到业界已有的成熟模式:

| 构想 | 业界对应 | 说明 |
|---|---|---|
| 分片自治 agent + CLI 命令 | **MCP (Model Context Protocol)** | Anthropic 2024 开放协议,标准化 LLM 连数据源/工具。每个 server 管一个域、暴露 tools(=CLI命令)、client 按需连。**最贴合金先生构想** |
| 调度 agent | **Orchestrator-Worker 多agent** | Anthropic 自己的 research 系统:lead agent 分解任务派给 subagents 再合并。本项目这次写文档的 workflow(17 agent 并行)就是雏形 |
| 不全塞、按需加载 | **Tool Retrieval / Deferred Loading** | 工具多时不一次性塞定义,按需检索加载。本对话环境的 `ToolSearch`(deferred tools)就是这个 |
| 调度知道"从哪取数" | **NL2SQL 的 Table Retrieval / Schema Linking** | 表多时先检索相关表再生成 SQL(Uber QueryGPT、Pinterest Querybot 等工业实践)。54 表已到该用这个的规模 |
| 口径统一、从哪取 | **Semantic Layer(语义层)** | dbt Semantic Layer / Cube.dev:把"指标定义+从哪取"集中抽象,上层不关心物理表 |

**结论**:这不是拍脑袋的想法,是业界正在落地的方向。尤其 **MCP 几乎就是为这个场景设计的**——金先生说的"每个 agent 管一个域、有 CLI 命令、能扩展",换成 MCP 术语就是"每个 MCP server 管一个域、暴露 tools、可加 tools"。

## 6. 一句话总结

方向对、跟业界(MCP / 多agent / 语义层)收敛,**但建议渐进落地而非一次大重构**;最大的两个坑是「跨域查询编排」和「agent 自增命令的失控风险」,设计时重点解决这两个。
